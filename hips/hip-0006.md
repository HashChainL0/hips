## Abstract

This HIP proposes optional association sets for withdrawals from shielded state. An association set is a public Merkle root over deposits that a publisher vouches for. A withdrawal may attach a proof that its deposit is a member of an accepted set, without revealing which member. Attaching a proof is the user's choice. A withdrawal without one stays valid.

## Motivation

Shielded state hides which deposit a withdrawal came from. That is the point, but it leaves honest users with no way to show that their funds did not come from a known bad deposit, short of handing over a view key that reveals far more. An association set gives them a narrower statement: "my deposit is one of these", where "these" is a list someone else maintains and anyone can inspect.

[Research note 08](https://github.com/HashChainL0/protocol-spec/blob/main/research/08-association-sets.md) compares the options and recommends optional, user chosen sets. The [shielded pool model](https://github.com/HashChainL0/shielded-pool-model) implements the check so the shape can be tested.

## Specification

Draft. Everything here is a proposal, and all parameter values are to be specified.

### Set roots

1. A set is a Merkle tree whose leaves are deposit labels. The label of a deposit is derived from its commitment and does not reveal the owner.
2. A publisher submits a set root to the network. The network keeps a bounded history of accepted roots per publisher.
3. A root is accepted for a window of `SET_ROOT_WINDOW` blocks. After the window it can no longer be used for new withdrawals.

### Withdrawals

1. A withdrawal MAY include an association proof: an accepted set root and a proof that the label of the withdrawn deposit is a leaf under that root.
2. The network MUST reject an association proof against a root that is unknown or outside its window.
3. The network MUST NOT reject a withdrawal because it has no association proof.
4. A change note created by a partial withdrawal keeps the label of the deposit it came from, so later withdrawals of the change can prove against the same sets.

## Rationale

Optional sets keep the exit guarantee: any valid note can always leave. Making sets mandatory would turn whoever publishes the accepted sets into a gatekeeper for every exit, which conflicts with the default-private design of the spec.

A bounded root window lets a publisher remove a deposit from a set and have the removal take effect for new withdrawals, the same way the pool bounds its history of note tree roots.

Carrying the deposit label on change notes avoids forcing the user to prove membership again from scratch after each split, at the cost of linking change notes to one origin inside the proof.

## Security considerations

- A set proof reveals the set chosen. A small set narrows the anonymity set of the claim to its size. Wallets should show the set size before a user attaches a proof.
- A withdrawal made just after a new root is accepted may be linked to the deposits that root added. Wallets should not attach a proof against a root that is only a few blocks old.
- A publisher can be wrong or dishonest. A set proof is a statement about the publisher's list, not about the funds.

## Open questions

1. Who may submit roots, and is there a cost to submitting one?
2. What is `SET_ROOT_WINDOW`?
3. Should a withdrawal be able to prove membership in more than one set at once?
4. Should change notes carry the label, or should membership be re-proven on each split?
