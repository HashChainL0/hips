## Abstract

This HIP proposes that private swaps between ETH and Monero are offered as direct corridors, one per connected network: Robinhood Chain, Base and Ethereum. A corridor holds the whole swap on its own network. It never routes through a second network and never includes a bridging step. The HIP also proposes a rollout order for the corridors and says which parts of the swap are shared between them and which are chosen per corridor.

## Motivation

The [Monero connection](https://github.com/HashChainL0/protocol-spec/blob/main/docs/11-connection-monero.md) describes the atomic swap once, as if there were a single ETH side. Hash Chain connects to several networks, and the timing and cost inputs of a swap differ by network: block time, how many blocks a claim needs to be included, how quickly a watcher sees an event, and whether a data posting fee counts against a gas limit. [HIP-3](hip-0003.md) already takes the block time of the contract chain as an input. Without a written rule for what a corridor is, two questions stay open. Can a swap start on one network and finish on another, and in what order should the corridors be opened?

A swap that crosses networks adds the failure modes of each network and of the step between them, and its deadlines would have to cover both. Keeping a corridor direct keeps the safety argument of the spec intact: the same state machine, the same roles, one set of deadlines on one clock.

## Specification

Draft. Everything here is a proposal, and all parameter values are to be specified.

### Corridor

A corridor is the pair ETH and XMR on exactly one connected network. A corridor MUST satisfy all of the following:

1. The swap contract, the ETH lock, the claim and the refund all happen on the corridor's network.
2. Both swap directions, ETH to XMR and XMR to ETH, are available. The ETH holder locks first and the XMR holder locks second, as in the spec, in both.
3. The swap MUST NOT route through another network. There is no bridging step inside a swap.
4. One set of `T0` and `T1`, computed by the rules of HIP-3, applies. Deadlines are never a sum over two networks.

A user who holds ETH on one network and wants XMR uses that network's corridor. Moving ETH between networks is not part of a swap. It is a separate action that uses the connections described in the [connections document](https://github.com/HashChainL0/protocol-spec/blob/main/docs/10-connections.md), and the swap starts only after it is done.

### Shared and per corridor

The following are the same in every corridor:

- The state machine, the roles and the transitions.
- The claim safety rule: a claim is not broadcast inside a safety margin before `T1`.
- The rule that the claimer submits their own claim, and that a relayer who is the counterparty is never used.
- The Monero side inputs of HIP-3: Monero block time, lock blocks, confirmations and the variance factor.

The following are chosen per corridor, as inputs to the HIP-3 formula and the claim safety margin:

- Block time of the corridor's network.
- Blocks a claim usually needs to be included.
- Worst case event detection latency.
- Whether a data posting component is charged inside the gas limit, which decides how a claim gas limit is sized.

Values for each corridor are to be specified and MUST come from measurement, not from this HIP.

### Rollout order

The proposed order of corridors is:

1. Robinhood Chain.
2. Base.
3. Ethereum.

Opening a corridor is a separate decision from specifying it. A corridor opens only when its inputs have been measured, its deadlines pass the HIP-3 constraints, and it has been reviewed. The order is a proposal for discussion, and no corridor has a date. It says nothing about the phases of the [roadmap](https://github.com/HashChainL0/protocol-spec/blob/main/docs/13-roadmap.md), and where the two differ the roadmap stays as written until a later HIP changes it.

### Reference model

The [xmr-swap-model](https://github.com/HashChainL0/xmr-swap-model) repository models the three corridors as plain data in priority order, with one chain profile each and both directions. Its profile numbers are illustrative placeholders. The model exists so the rules above can be run and argued about. It is not a measurement of any network.

## Rationale

Direct corridors keep the claim safety argument local. A cross-network swap would need the deadlines of two networks to line up, and a stall on either would lock the funds of the party who already locked. It would also add a place where a relayer or a bridge can see or influence the swap, which works against the privacy goal.

Reading the swap per network instead of with one global parameter set reflects that the inputs really differ. A single conservative set would be safe everywhere and too slow to be useful where the network is fast, and a single optimistic set would be unsafe where it is not.

Alternatives considered:

- **One corridor with bridged ETH.** Rejected because it adds a bridging step to every swap and merges two sets of deadlines.
- **No stated order.** Rejected because the corridors depend on measurement work that will not finish at the same time, and a written order lets reviewers see what comes first and why it can be challenged.

## Security considerations

- **Per corridor parameters.** A corridor with optimistic inputs can let a claim miss `T1` and expose the secret, as described in the claim safety rule. Inputs MUST be measured, and a corridor MUST NOT open on the placeholder values of the reference model.
- **Network faults.** A halt or censorship on the corridor's network can delay a claim past `T1`. This risk exists on every corridor and is tracked as an open research question in the spec.
- **Privacy.** A direct swap exposes the corridor used. A corridor with few users has a small anonymity set. How the set is measured and what can be done about a thin corridor is to be specified.
- **Confusion with bridging.** Wallets MUST NOT present a corridor swap as a cross-network transfer, and MUST NOT offer to move ETH between networks as part of one swap flow without showing it as a separate step.

## Open questions

- Whether the swap contract lives on each connected network or on Hash Chain with the connected network supplying only the ETH side. The corridor rules above hold in both cases, the deadline inputs differ.
- The measurements needed to open each corridor, and who reviews them.
- Whether a corridor can be closed again, and what happens to swaps in flight when it is.
- How the claim gas limit is sized on a corridor where the data posting component moves.
- Whether the rollout order should follow measurement results instead of being fixed in advance.
