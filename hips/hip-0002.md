## Abstract

This HIP proposes how a Hash Chain wallet derives view keys that are limited by direction (incoming, outgoing or both), by date range and optionally by asset or account. A scoped view key gives read-only visibility into part of a user's history and can never spend. Revocation stops future visibility only.

## Motivation

Hash Chain accounts are private by default. People and businesses still need to show their history to an accountant, auditor or tax authority, and they should be able to show only what is needed. A single all-seeing view key forces a bad choice between showing everything and showing nothing. The protocol spec describes scoped view keys in [docs/08](https://github.com/HashChainL0/protocol-spec/blob/main/docs/08-proofs-and-view-keys.md) as a design sketch. This HIP turns that sketch into a proposal with testable rules. Private, not shady: privacy is the default and disclosure is the user's decision.

## Specification

Everything below is a draft design. Names and encodings are to be specified.

### Key hierarchy

A wallet holds one master secret. From it the wallet derives:

- a spending key,
- a nullifier key,
- one or more view keys.

A view key MUST be able to decrypt note payloads. A view key MUST NOT allow deriving the spending key or the nullifier key. Deriving a view key from the master secret is one way, so a holder cannot go back up the tree.

### Scope dimensions

| Scope | How it is enforced |
| --- | --- |
| Direction | Separate incoming and outgoing view keys. A holder of one cannot read the other. |
| Date range | Keys are derived per epoch. A holder given a range receives only the epoch keys inside it. |
| Asset or account | A view key branch is derived per asset or per account. A holder receives only the branches chosen. |

A wallet MUST show the user the exact scope before a view key is shared, in plain language, for example "incoming payments, 1 January to 31 December, one account".

### Epochs

Time is divided into epochs. Notes created in an epoch are encrypted to that epoch's view key. The length of an epoch is to be specified. Epoch boundaries are defined on Hash Chain time so that wallets agree on them.

### Sharing

To share, the wallet derives the epoch keys for the chosen range, direction and branches, and gives them to the recipient. The recipient reads the matching history with their own tooling. Delivery of the keys is outside this HIP.

### Revocation

Revocation applies to the future only.

1. The wallet stops sharing further epoch keys with the holder.
2. The wallet moves new activity to a fresh key branch that the old view key cannot read.

Data the holder already viewed cannot be unseen. Wallets MUST say this when a view key is created and again when it is revoked.

### What a view key never does

- It never grants spending power.
- It never shows activity on other networks, unless that activity touches Hash Chain.
- It never reveals the identity behind an account. Identity attributes are handled by credentials, not view keys.

## Rationale

Per epoch derivation was chosen because it gives date scoping without asking the validators or any other party to know about the scope. It keeps the scheme in the wallet. The cost is that granularity is limited by epoch length, and that revocation cannot reach into the past. The second limit is true of any scheme, because information that was read cannot be taken back. Making it explicit in the wallet is better than implying otherwise.

Separate keys for incoming and outgoing history were chosen over one key with a filter, because a filter is a promise by the holder, while separate keys are enforced by cryptography.

Credentials (proving one fact without showing history) are a different tool and are not part of this HIP.

## Security considerations

- **Resale and leakage.** A view key can be copied. The holder can share it onward. The user should share only with trusted parties and only the needed scope.
- **Revocation is not deletion.** Reports the holder already saved remain with them.
- **Spent state.** A holder who can see a note may be able to tell when it is spent only if the scheme lets them derive its nullifier. Whether outgoing visibility reveals nullifiers is to be specified. If it does, a holder with an incoming key could learn more than intended, so the default is that incoming keys do not reveal spent state.
- **Metadata at the edges.** Epoch boundaries are visible to the holder. A narrow range may let the holder infer activity just outside it. Wallets should warn when a range is very short.
- **Key storage.** View keys are secrets. Wallets MUST store them as carefully as other wallet secrets.
- **Mistakes in scope.** A scope chosen by mistake cannot be shrunk after sharing. The interface must make the scope hard to get wrong.

## Open questions

- The exact derivation tree and the length of an epoch.
- Whether a view key can be bound to a named recipient to discourage resale.
- Whether outgoing visibility reveals nullifiers, and how to avoid it.
- Optional signed reports so an auditor can attest to what they saw.
- Wallet interface for choosing scopes without mistakes.
- Interaction with credentials and the proof of source of funds described in the spec.
