## Abstract

A Hash Chain Improvement Proposal (HIP) is a written design document for a change to Hash Chain or its surrounding practice. This HIP defines what a HIP is, the kinds of HIP, the stages a HIP passes through, and who maintains the process.

## Motivation

Hash Chain is a network with its own validators, privacy at the base layer and connections to other networks. Decisions about it should be written down, discussed in public and kept as a record. A common format makes proposals easier to read, review and compare. It also gives reviewers a stable place to find the reasoning behind a decision, including the options that were rejected.

## Specification

### What a HIP is

A HIP is a document in the `hips/` directory of this repository, named `hip-NNNN.md`. It describes one change, gives the reasoning for it and records the objections raised. HIPs are proposals. A HIP does not describe something that exists until its text says so.

### Categories

| Category | Scope |
| --- | --- |
| Core | Consensus, validators, staking, accounts, proofs, privacy mechanisms |
| Networking | Peer to peer communication, validator messaging, data propagation |
| Interface | APIs, SDKs, wallet behaviour, standards for apps and tokens |
| Connection | Links to other networks: Ethereum, Base, Robinhood Chain, Monero |
| Meta | The HIP process itself and related practice |
| Informational | Background, guidelines or design notes with no required adoption |

### Status lifecycle

| Status | Meaning |
| --- | --- |
| Idea | Discussed informally in an issue. Not yet a document. |
| Draft | A pull request is open and the author is working on the text. |
| Review | The author asks for wider review. The text is complete enough to criticise. |
| Last Call | A final review window. Any objection must be raised now. |
| Final | Accepted. Changes are limited to corrections and clarifications. |
| Withdrawn | The author has withdrawn the proposal. The number is not reused. |
| Stagnant | A Draft or Review HIP with no activity for six months. The author or anyone else may revive it by moving it back to Draft. |

Normal path: Idea, Draft, Review, Last Call, Final. A HIP may become Withdrawn or Stagnant at any point before Final.

### Required sections

Every HIP has this front matter: `hip`, `title`, `author`, `status`, `category`, `created`. The optional field `requires` lists other HIP numbers this one depends on.

Every HIP has these sections, in this order: Abstract, Motivation, Specification, Rationale, Security considerations, Open questions. Informational and Meta HIPs may state "none" under Security considerations, with a reason.

### Submitting a HIP

1. Open an issue with the "HIP idea" template and discuss the idea in public. Check the index in the README for related work.
2. Copy `hip-template.md`, fill it in and open a pull request. One HIP per pull request.
3. An editor assigns the number and merges the pull request as Draft once the form is correct. Merging as Draft is not an endorsement of the content.
4. The author moves the HIP through Review and Last Call by pull request, responding to feedback in the open.
5. An editor moves the HIP to Final when the Last Call window ends without unresolved objections.

### Editors

HIP editors are the maintainers of this repository. Editors check form, numbering, links and style. They do not judge whether a design is good. Technical disagreement is resolved in the open, in the pull request.

### Last Call

Last Call lasts at least fourteen days. An unresolved objection returns the HIP to Review.

### Changing a Final HIP

A Final HIP may receive corrections and clarifications. A change in meaning requires a new HIP that names the earlier one.

## Rationale

The process is modelled on Ethereum Improvement Proposals and Bitcoin Improvement Proposals, which have a long record of working in public and keeping a readable history. The lifecycle is kept small. Editors check form, not merit, so that no one has to defend a design to gatekeepers before it can be discussed. Stagnant exists so the index stays honest about which proposals are alive.

## Security considerations

A process document has no direct security impact. The process does affect how safely changes are made: the required Security considerations section and the public Last Call window are meant to make sure risks are raised before a design is accepted. Vulnerabilities in a proposal should be reported privately, as described in SECURITY.md.

## Open questions

- How the process interacts with validator signalling once a validator network exists.
- Whether a Core HIP should need a reference implementation or a test vector set before Final.
- How editors are added and removed as the maintainer group grows.
