## Abstract

This HIP proposes how the two deadlines `T0` and `T1` of the Hash Chain and Monero atomic swap are chosen, and which constraints any chosen values must satisfy. It defines the formula, lists the inputs, and gives a worked example. All numbers are placeholders for discussion, not recommendations.

## Motivation

The [Monero connection](https://github.com/HashChainL0/protocol-spec/blob/main/docs/11-connection-monero.md) uses two deadlines on Hash Chain time. `T0` is the deadline by which the ETH holder must signal that the XMR lock is confirmed. `T1` is the deadline for the XMR holder to claim after that signal. The spec leaves their lengths "to be specified". Values that are too short can let a refund beat a valid claim, or leave the ETH holder no time to signal ready on a good lock. Values that are too long leave funds frozen for longer than needed when a party disappears. The deadlines need a written derivation that reviewers can attack.

## Specification

Draft. Parameters are proposals. The reference calculator is the [xmr-swap-model](https://github.com/HashChainL0/xmr-swap-model) repository, a research model that holds no keys and touches no network.

### Inputs

| Name | Meaning |
| --- | --- |
| `ethSideBlockTimeSec` | Block time of the chain running the swap contract. Deadlines are aligned to it. |
| `moneroBlockTimeSec` | Target Monero block time. |
| `moneroLockBlocks` | Blocks before a Monero output is spendable. |
| `requiredConfirmations` | Confirmations the ETH holder waits for before signalling ready. |
| `moneroBlockVarianceFactor` | Multiplier, because Monero block times are random. |
| `counterpartyLockAllowanceSec` | Time for the XMR holder to see the ETH lock and broadcast the XMR lock. |
| `ethHolderOnlineMarginSec` | Slack so an ETH holder who is briefly offline can still signal ready before `T0`. |
| `xmrHolderOnlineMarginSec` | Slack so an XMR holder who is briefly offline can still claim before `T1`. |
| `claimInclusionBlocks` | Contract blocks allowed for the claim to be included. |

### Formula

```
confirmationWait = requiredConfirmations * moneroBlockTimeSec * moneroBlockVarianceFactor
T0 = ceil_to_block(counterpartyLockAllowance + confirmationWait + ethHolderOnlineMargin)
claimWindow = ceil_to_block(xmrHolderOnlineMargin + claimInclusionBlocks * ethSideBlockTimeSec)
T1 = T0 + claimWindow
```

Both deadlines are durations counted from the ETH lock, on Hash Chain time.

### Constraints

Any chosen `T0` and `T1` MUST satisfy:

1. `T0` and `T1` are positive.
2. `T1` is later than `T0`. Otherwise `Ready` can never be claimed before it can be refunded.
3. `T0` is at least the lock allowance plus the confirmation wait. The ETH holder must be able to signal ready on a valid lock.
4. `requiredConfirmations` is at least `moneroLockBlocks`. A Monero output is not spendable earlier, so a sweep after ready could fail.
5. `T1` is at least `moneroLockBlocks * moneroBlockTimeSec * moneroBlockVarianceFactor`. A refund should not be reachable before the Monero lock can be spent.
6. `T1 - T0` is at least the XMR holder's online margin plus claim inclusion time.
7. `T0` and `T1` are whole multiples of the block time, so deadlines fall on block boundaries.

### Worked example

This example uses the placeholder inputs of the reference model. It is an example only.

| Input | Value |
| --- | --- |
| `ethSideBlockTimeSec` | 12 |
| `moneroBlockTimeSec` | 120 |
| `moneroLockBlocks` | 10 |
| `requiredConfirmations` | 10 |
| `moneroBlockVarianceFactor` | 2 |
| `counterpartyLockAllowanceSec` | 3600 |
| `ethHolderOnlineMarginSec` | 14400 |
| `xmrHolderOnlineMarginSec` | 21600 |
| `claimInclusionBlocks` | 20 |

Result:

- Confirmation wait: 2400 s.
- `T0`: 20400 s (about 5.67 hours, 1700 blocks).
- Claim window: 21840 s (1820 blocks).
- `T1`: 42240 s (about 11.73 hours, 3520 blocks).

All seven constraints hold for these values.

## Rationale

Splitting each deadline into named components makes every assumption visible and separately arguable, instead of hiding them in one opaque number. The variance factor exists because Monero block times are random, so ten blocks can take much longer than ten times the target. Deadlines are counted on Hash Chain time because the swap contract runs there, and Monero offers no timelocks.

The margins are the real policy choice. A longer margin protects users who go offline and costs time when a swap fails. This HIP does not claim the example margins are right. It asks reviewers to say what a user should be expected to tolerate.

## Security considerations

- **Halts and censorship.** A long halt or censorship of the validator set can make deadlines pass while a party cannot act. The design intends this to cause a refund and not a theft. See the spec section on security and trust.
- **Too short.** If `T0` is too short, a valid lock may not reach enough confirmations in time. If the claim window is too short, an XMR holder may be unable to get a claim included.
- **Too long.** Long windows extend how long a griefing counterparty can freeze funds. A deliberately absent ETH holder can freeze the XMR holder's funds after both locks and before ready. Timelock lengths do not fix this alone. A bond, a different lock order or a watchtower may be needed.
- **Reorganizations.** A Monero reorganization deeper than the confirmation count could invalidate a lock after ready. The confirmation count is therefore a security parameter, not only a convenience.
- **Clock and block time drift.** Deadlines are in seconds but enforced in blocks. If the average block time of the contract chain changes, real time windows change with it.
- **Model is not a proof.** The reference model checks arithmetic and state transitions. It does not run cryptography and is not audited.

## Open questions

- Real values for each input, and who decides them. The model values are placeholders, tracked in [protocol-spec issue 5](https://github.com/HashChainL0/protocol-spec/issues/5).
- Whether parameters are fixed in the contract, set per swap by the parties within bounds, or governed.
- How wallets warn users about the need to come back online.
- Whether the signal ready step can be replaced by something that needs less online presence from the ETH holder.
- The link between these windows and a griefing bond or watchtower design.
- Whether the confirmation count should scale with swap size.
