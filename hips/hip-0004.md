## Abstract

This HIP proposes that every update on Hash Chain pays its fee in ETH from the sender's shielded balance, inside the same zero-knowledge proof, with the fee fixed by the transaction's shape class and the current epoch. No public fee payer account is needed, no tip exists, and the fee field reveals only a coarse shape class.

## Motivation

The [fee document](https://github.com/HashChainL0/protocol-spec/blob/main/docs/12-fees.md) says fees are paid in ETH and bound to the proof, and leaves private payment open. On most chains the fee payer is a visible account. If a Hash Chain update needed one, each private transfer would be linked to a public identity when it is paid for. A fee amount that varies per transaction also fingerprints wallets and reveals urgency. The comparison of options is in [research note 07](https://github.com/HashChainL0/protocol-spec/blob/main/research/07-fees-and-fee-privacy.md).

## Specification

Draft. Everything here is a proposal, and all parameter values are to be specified.

### Shape classes

An update belongs to exactly one shape class, defined by its number of input notes, output notes and public value movements. Wallets MUST pad updates to a listed class. Encrypted note payloads MUST be padded to the fixed size of that class. The list of classes is to be specified. A small list keeps the anonymity set of each class large.

### Fee schedule

For each epoch, the validator set publishes a fee unit and, for each shape class, a weight. The fee for an update is:

```
fee = feeUnit(epoch) * weight(shapeClass)
```

The weights SHOULD reflect proof verification cost and data size. How `feeUnit` is set, and how it responds to load, is to be specified.

### Public inputs

The transfer proof ([03](https://github.com/HashChainL0/protocol-spec/blob/main/docs/03-accounts-and-private-transfers.md)) gains these public inputs:

| Field | Meaning |
| --- | --- |
| `fee` | Amount of ETH taken from the sender's input notes, in the smallest unit |
| `feeEpoch` | Epoch whose schedule the fee was computed from |
| `shapeClass` | Identifier of the update's shape class |

The value balance rule becomes: sum of input values plus `publicValueIn` equals sum of output values plus `publicValueOut` plus `fee`, per asset, where `fee` counts only against ETH.

### Validator rules

Validators MUST reject an update if any of the following holds:

1. `shapeClass` is not a listed class.
2. `feeEpoch` is not the current epoch or the one immediately before it.
3. `fee` is not exactly `feeUnit(feeEpoch) * weight(shapeClass)`. Overpayment and tips are rejected, so the fee carries no information beyond the class and epoch.
4. The proof does not verify.

An update that satisfies the rules is applied, and `fee` is added to the fee pool of the epoch in which the update is finalized.

### Fee pool

The fee pool is a public per-epoch balance of ETH on Hash Chain. It is distributed to validators for that epoch by a rule to be specified, such as stake-weighted shares for validators that took part in finality. Distribution is not tied to which validator included a given update.

### Updates that move value to a connection

A release to a connected network pays two things: the Hash Chain fee above and the cost on the destination network ([10](https://github.com/HashChainL0/protocol-spec/blob/main/docs/10-connections.md)). The second is a separate bound field, `connectionFee`, as already described for provider fees in the spec. Its pricing is to be specified.

### Sponsored fees

A sponsor MAY give users fee credits that a wallet redeems without revealing which credit belongs to which user. The mechanism, using blind or anonymous credentials, is to be specified. A credit, when redeemed, funds the `fee` of an update whose sender has no ETH note.

## Rationale

Paying inside the proof removes the payer. Fixing the fee by shape and epoch removes the tip, and with it the most identifying fee behavior. Zcash and Penumbra both pay from shielded balances, and Zcash sizes fees by the number of logical actions, which supports the shape-based schedule. A relayer paid out of the transfer, as in Tornado Cash relayers, was considered and rejected as the default because it adds a counterparty who sees requests and can censor them, and the relayer fee stays public. A paymaster in the ERC-4337 style was rejected for the same reason. Both remain compatible with this design as optional services built on top.

The two-epoch acceptance window exists so an update built just before an epoch change is not rejected. It reveals only that the update was built near a boundary.

## Security considerations

- **Privacy.** The fee reveals the shape class and a time within about one epoch. A small number of classes keeps each class large. Rare classes leak more, so the class list should stay short and wallets should default to the most common class.
- **Spam.** Every update spends real ETH from a real note, so spam has a cost. A fee set too low makes spam cheap. A fee set too high prices out small payments. The load response is to be specified.
- **Fee unit manipulation.** If validators set `feeUnit` themselves, a majority could raise fees. Bounds on change per epoch SHOULD apply. This depends on the staking design in [research note 01](https://github.com/HashChainL0/protocol-spec/blob/main/research/01-stake-and-slashing.md).
- **Bootstrap.** A new user with no ETH note cannot pay. Sponsored credits or a fee allowance from a connection deposit are possible, and both are to be specified.
- **Sponsor privacy.** A badly designed credit scheme lets the sponsor link redemptions to users. Credits MUST be unlinkable to the user at redemption.
- **Soundness.** An error in the value balance rule could create ETH. The rule MUST be covered by independent circuit review, like the rest of the proof ([09](https://github.com/HashChainL0/protocol-spec/blob/main/docs/09-security-and-trust.md)).
- **Timing.** Fee pool distribution should not allow one validator to profit from reordering updates.

## Open questions

- The list of shape classes and their weights.
- How `feeUnit` reacts to congestion without tips.
- Whether any fee could be hidden behind a committed value.
- Credit design for sponsored fees.
- How data availability costs enter the weights if storage nodes are separate.
- Whether the fee asset can ever differ from ETH.
